## Online migration compatibility period and forward recovery

S-11 is a forward-only, three-stage release. First apply `00000` expand and
`00001` schedule controls while the S-10 application remains available. Both
fail fast with a five-second lock timeout. The compatibility trigger keeps old
S-10 writers valid and fills S-11 lifecycle metadata during binary rollout.

Run `SELECT public.backfill_ai_uploads_s11(500);` in separate autocommit
transactions until it returns `0`. Each call locks at most 500 rows with
`SKIP LOCKED`; it is safe to retry or run concurrently. Then apply `00002`,
which rejects incomplete data before validating the already enforced NOT VALID
constraints.

Forward recovery is additive: never drop expanded columns or S-10 functions.
After a lock timeout, inspect the migration ledger and schema, then replay the
same idempotent expand file with statement-level autocommit during a quieter
window. Its constraint replacement is one atomic statement. After backfill
interruption, resume bounded batches. If validation reports
`S11_BACKFILL_INCOMPLETE`, finish the batches and reapply validation. Keep the
compatibility trigger for at least one full application rollback window so an
application rollback can continue using S-10 contracts against the expanded DB.

## Monitoring

- Alert on the oldest visible Queue message and on `delete_due_at < now()` rows that remain outside an active cleanup claim.
- Logs may contain validated invocation ID, entity IDs, provider, safe status/code, attempt, duration, and enumerated reason only. `worker_recoverable`, `worker_poison`, and `worker_duplicate` use the same allowlist and must never carry raw exception, request, response, payload, prompt, card, image, URL query, Authorization, or secret values.
- A terminal duplicate should increase ACK observations but not provider, quota, card, illustration, or object counts. A normal terminal provider/Storage failure or retry exhaustion emits one `worker_failure` only after DB terminal confirmation, never zero or multiple. Retry-persistence faults, ambiguous DB outcomes, claim loss, and unconfirmed terminal persistence emit zero `worker_failure`; monitor their `worker_recoverable` events and leave the message recoverable under the existing visibility/fencing rules.
- Configuration, image/input validation or decode, provider/Storage contract, poison, duplicate/business result, setup, claim loss, and ambiguous DB/RPC/network paths emit zero `worker_failure`. Poison is recorded only after strict `ack_inert_delivery=true`, correlated by queue message ID; an unconfirmed ACK remains recoverable and unarchived.
- Cleanup authentication requires a trimmed non-empty configured secret. Missing/blank/read/setup faults return safe 500 with one allowlisted cleanup event; valid-secret missing/mismatch headers return log-free 401.
- Failure-response reconciliation must match the persisted terminal message ID and claim token. A stale worker observing a later claim's failed job is `claim_lost`, not another terminal failure observation.
- Alert on undispatched `ai_worker_log_outbox` rows older than one worker interval. Failure/poison/duplicate rows are committed with terminal/archive, and retries retain the same `eventId`; downstream counting must deduplicate that ID.
- An outbox claim or completion fault after terminal/archive commit must not change the terminal result or suppress last-consumer source release. The stable event remains lease-reclaimable; monitor the durable row and never log the caught transport exception or raw response.
- Cleanup claims are identified by tracking ID, bucket, path, and UUID token. Treat `CLAIM_LOST` as stale work, never retry completion against a newer lease. Source/raw due together must appear as two claims in the first eligible run.
- Any transaction touching these row classes must preserve the production lock order: existing cards by UUID, then illustrations by UUID, then illustration lifecycle/tracking rows by UUID. Card INSERT has no pre-existing card row and therefore enters at illustrations. Tracking-only claim/recovery paths must never acquire an earlier class later. Keep the bounded complete-vs-authenticated-attach two-session gate in both scheduling orders before deploying lock changes.

## Rollback and compensation rehearsal

1. Stop new enqueue at the caller and invoke `deactivate_ai_card_async_schedules()`.
2. Keep Queue messages, batches, jobs, status rows, and object tracking. Do not delete or recreate the queue.
3. Status remains available while schedules are inactive. Audit queued/processing jobs and due cleanup rows.
4. Roll back Edge code to the last known-good worker. Do not automatically fall back to the synchronous S-08 path or another provider.
5. For uploaded but unfinalized objects, use tracking-driven Storage API deletion. Never delete rows directly from `storage.objects`.
6. Restore in this order: deploy worker, authenticated single-message smoke, deploy cleanup, cleanup dry-run, then schedule activation.
7. Use a forward fix for schema corrections. Do not apply a destructive down migration to populated tables or queues.

The local implementation completed code and mock-smoke preparation only. Hosted deploy, remote migration application, service-auth smoke, Vault changes, and schedule activation remain an explicit next gate.

Age cleanup is exact: source/orphan rows are protected through 23:59:59 and become eligible at 24:00:00. Illustration `delete_pending` created by the last card-reference deletion is eligible immediately and retains that intent after failed Storage deletion; it must not fall back to age cleanup. Every retry rechecks the cleanup lease, owner path, and same-owner reference count 0. Referenced/re-referenced objects and owner/path mismatches are always protected.
