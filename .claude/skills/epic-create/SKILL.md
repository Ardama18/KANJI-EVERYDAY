**コマンドコンテキスト**: 対話的にエピック要件を収集し、epic.md とディレクトリを自動生成

## 責務

**エピック定義の作成のみ担当**（ストーリー分解は `/epic-to-stories` が担当）

- ユーザーとの会話を通じて要件を段階的に収集
- エピックID を `specs/epics/` スキャン（`E-*` + 旧 `TC-E-*`）で自動採番
- ディレクトリ作成と epic.md 生成
- 次のアクション（`/epic-to-stories`）を案内

**責務境界**：
- ✅ 対話による要件収集（目的・スコープ・技術方針・設計方針等）
- ✅ エピックID 自動採番（`specs/epics/` 内の `E-*` + 旧 `TC-E-*` スキャン → 最大番号+1）
- ✅ ディレクトリ作成（`specs/epics/E-{ID}-{title}/`）
- ✅ epic.md 生成（既存エピックの構造に準拠）
- ❌ ストーリー分解（`/epic-to-stories` が担当）
- ❌ 設計・実装（`/implement` が担当）

## 入力

```
/epic-create [初期説明テキスト]
```

**引数**：
- `[初期説明テキスト]` (任意): エピックの初期説明。指定するとヒアリングの起点として活用

## 実行フロー

### Phase 1: 初期情報の把握

```
1. 引数チェック:
   - 初期説明テキストがある → Phase 2 のヒアリングの起点に活用
   - なし → 白紙から会話開始

2. 既存エピック一覧を確認:
   - specs/epics/ 配下を Glob でスキャン（E-* および旧 TC-E-* の両方）
   - 重複テーマの回避、関連エピックとの整合性確認に使用

3. プロジェクトコンテキスト把握:
   - .claude/rules/project-context.md を参照し、ドメイン・技術スタック・アーキテクチャ前提を認識
```

### Phase 2: 対話による要件収集

**収集すべき情報**（以下の順序で段階的にヒアリング）:

```
Round 1 - 核心の把握:
  「どんなエピックを作りたいですか？」
  収集項目:
  - エピックタイトル（短い名前）
  - 目的（なぜこの機能が必要か）
  - スコープ（何を含み、何を含まないか）

Round 2 - 技術方針の確認:
  「技術的な方針を確認させてください」
  収集項目:
  - 追加技術スタック（既存スタック以外に必要なライブラリ・ツール）
  - 既存モジュールとの関連（どのモジュールに影響するか）
  - DB スキーマ変更の有無

Round 3 - 設計方針の確認:
  「共通設計方針を確認させてください」
  収集項目:
  - 共通設計方針（全ストーリーで適用するルール）
  - ストーリー間で共有する設計・実装（共通モジュール、データ構造、インターフェース、ユーティリティ）
  - API 設計方針（エンドポイント設計、レスポンス形式）

Round 4 - 品質・リスクの確認:
  「品質要件とリスクを確認させてください」
  収集項目:
  - セキュリティ要件
  - パフォーマンス要件
  - テスト戦略
  - 想定リスクと対策
```

**ヒアリングのルール**:
- 各 Round は 1-2 質問に絞る（ユーザーの負担を最小化）
- ユーザーが十分な情報を提供した場合、後続の Round をスキップ可能
- 初期説明テキストで既に明確な項目はスキップ
- 不明な項目はプロジェクトコンテキストから推定し、ユーザーに確認
- 「特になし」「おまかせ」等の回答は、既存エピックのパターンから推定

### Phase 3: epic.md ドラフト確認

```
1. 収集した情報から epic.md のドラフトを生成
2. ドラフト全文をユーザーに提示

3. [停止: ユーザー承認待ち]
   - 承認 → Phase 4 へ
   - 修正要求 → 修正してドラフトを再提示
   - キャンセル → 処理中断
```

### Phase 4: ID 自動採番とディレクトリ作成

```
1. エピックID 自動採番:
   - specs/epics/ 配下をスキャンし、全ディレクトリ名からIDの数値部分を抽出
     - 新形式: E-{N}-... → N を抽出
     - 旧形式: TC-E-{N}-... / TC-E--{N}-... → N を抽出
   - 全形式の最大番号+1 で新しい ID を決定
   - 例: 既存が TC-E-01 〜 TC-E-06 → 新規は E-07
   - 新規 ID フォーマット: E-{ゼロ埋め2桁}（例: E-07, E-08）

2. ディレクトリ作成:
   - specs/epics/E-{ID}-{kebab-case-title}/ を作成
   - タイトルの kebab-case 変換ルール:
     - 日本語タイトルの場合は英語に意訳して kebab-case 化
     - 例: 「AI アドバイザー機能」→ ai-advisor-feature

3. epic.md 書き込み:
   - Phase 3 で承認されたドラフトを書き込み
   - 「## このエピックのストーリー」セクションは空で作成
     （/epic-to-stories で後から追記）
```

### Phase 5: 完了報告

```
1. 完了メッセージを表示:

   エピック作成完了

   **エピック情報**:
   - エピックID: E-{ID}
   - タイトル: {タイトル}
   - ディレクトリ: `specs/epics/E-{ID}-{title}/`
   - ファイル: `specs/epics/E-{ID}-{title}/epic.md`

   **次のアクション**:
   ストーリー分解を行うには以下を実行してください:
   /epic-to-stories specs/epics/E-{ID}-{title}
```

## エラーハンドリング

### 既存エピックとの重複検知
```
既存エピック一覧を確認した結果、類似のエピックが見つかりました:
- E-{ID}: {タイトル} (specs/epics/E-{ID}-{title}/)

新規作成を続行しますか？ (yes/no)
```

### ディレクトリ作成失敗
```
ディレクトリの作成に失敗しました: specs/epics/E-{ID}-{title}/
エラー: {エラーメッセージ}

対処: ディレクトリの権限を確認してください。
```

## 使用例

### 初期説明テキストあり
```
/epic-create 子どもの学習進捗を AI で分析し、親にレポートする機能
```

### 初期説明テキストなし（白紙から会話開始）


## 品質基準

### 必須条件
- [ ] 対話による要件収集が段階的に行われること
- [ ] エピックID が既存エピックと重複しないこと（自動採番）
- [ ] epic.md が既存エピックの構造に準拠していること
- [ ] ドラフトがユーザーに提示・承認されてから書き込まれること
- [ ] 「このエピックのストーリー」セクションが空で作成されること

### 推奨条件
- [ ] ヒアリングが 3-4 ラウンド以内で完了すること
- [ ] 既存エピックとの重複が検知・報告されること
- [ ] 次のアクション（/epic-to-stories）が明確に案内されること
