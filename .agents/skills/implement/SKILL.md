## 並列実行時の作業分離（必須）

複数のエージェントを同一ワークツリー（同一フォルダ）で同時実行すると、`git diff`/`git status` に他エージェントの差分が混入し、`git commit` 時に誤って別タスクの変更を含めやすい。

**方針**: ストーリー単位（またはエージェント単位）で `git worktree` を作り、**別ブランチ・別フォルダ**で作業する。

### 運用ルール
- 同時並行で動くエージェントは、原則として **別worktree** を使用する（共有ワークツリー禁止）
- `git commit` は、そのエージェントの worktree でのみ行う（別worktreeの差分を混ぜない）
- worktree の配置は、元ワークツリーを汚さないよう `tmp/worktrees/...` を推奨（このリポジトリは `tmp/` が `.gitignore` 済み）

### worktree 作成コマンド例
```bash
# 例: S-05 family-sharing を分離して進める
git worktree add -b story/S-05-family-sharing tmp/worktrees/S-05-family-sharing
cd tmp/worktrees/S-05-family-sharing
```

### 完了時の振る舞い（推奨）
- **デフォルト**: PR作成・レビュー対応のため worktree は残す（すぐ消さない）
- **クリーンアップ条件**: PRがマージ済み、または「当面このストーリーを触らない」ことが確定したら worktree を削除する
- 削除は `--force` を使わない（未コミット変更の破棄につながるため）。削除に失敗したら `git status` を確認して原因（未コミット/未push等）を解消してから再実行する

```bash
# main worktree 側で実行（削除対象のworktreeには cd しない）
git worktree list
git worktree remove tmp/worktrees/S-05-family-sharing
git worktree prune
```

注: worktree を消してもブランチは消えない。ブランチ削除は PR マージ後に必要なら実施（`git branch -d ...`）。`-D` は原則使わない。

### fallback（worktreeが使えない場合）
- commit前に `git diff --name-only` を確認し、**現在タスクの対象ファイル以外**の差分がある場合は commit を中断する
- 中断後、ユーザーへ「差分混入がある」旨とファイル一覧を提示し、分離方法（worktree化、または作業順の調整）を提案する

## 実行判断フロー

### 1. 現在状況の判定
指示内容: $ARGUMENTS

現在の状況を判定：

| 状況パターン | 判定基準 | 次のアクション |
|------------|---------|-------------|
| 新規ストーリー（ストーリーディレクトリ付き） | ストーリーディレクトリパスが指定されている | ローカルの story.md / requirements.md / meta.json をRead→ストーリー情報取得→requirement-analyzerから開始（ストーリー情報+追加指示を含む） |
| 新規要件（ディレクトリパスなし） | 既存作業なし、新しい機能/修正依頼 | requirement-analyzerから開始（機能説明+追加指示を含む） |
| フロー継続 | 既存ドキュメント/タスクあり、継続指示 | sub-agents.mdのフローで次のステップを特定 |
| 品質エラー | エラー検出、テスト失敗、ビルドエラー | quality-fixer実行 |
| 不明瞭 | 意図が曖昧、複数の解釈が可能 | ユーザーに確認 |

### 2. 継続時の進捗確認
フロー継続の場合、以下を確認：
- 最新の成果物（要件定義書/ADR/Design Doc/作業計画書/タスク）
- 現在のフェーズ位置（要件/設計/計画/実装/品質保証）
- sub-agents.mdの該当フローで次のステップを特定

### 3. 次のアクション実行

**sub-agents.mdを必ず参照**：
- **Figma統合判定**: ユーザー指示またはストーリー情報にFigma URL（https://www.figma.com/...）、デザイン仕様書言及、「Figmaデザインに従う」等が含まれる場合 → Figma統合フロー適用
- 規模別フロー（大規模/中規模/小規模）を確認
- 自律実行モードの条件を確認
- 必須停止ポイントを認識
- フローに定義された次のサブエージェントを呼び出す

## 🎯 オーケストレーターとしての必須責務

### タスク実行時の品質サイクル管理
**原則**：task-executor実行後は、差分混入を防ぐために「変更の区切り」を作ってから次へ進む。

1. （推奨）コミット単位に達している場合は `git commit` を実行（Bashツール使用）
2. （バッチコミット運用の場合）コミットしない場合でも、`git diff --name-only` で想定外ファイル混入がないことを確認してから次タスクへ進む
3. 次タスクの特定と実行または完了報告

**コミット粒度**：`task-decomposer` が定義した粒度、またはユーザーの追加指示を優先する。

### task-executor呼び出し時のタスク指定【必須】
**基本原則**: task-executorには実行すべきタスクファイルを明示的に指定する

**粒度指定（任意）**: タスクファイルを「1つずつ」実行するか、「まとめて」実行するかを明示できる。
- `single`（デフォルト）: 1つのタスクファイルのみを実行
- `batch(N)` : 連番で最大N個のタスクファイルをまとめて実行（同一phase内を推奨）
- `phase` : 同一phaseの未完了タスクをまとめて実行

**呼び出し形式**:
```
subagent_type: "task-executor"
prompt: |
  タスクファイル:
  - specs/stories/{STORY_ID}-{title}/tasks/task-{feature}-phase1-001.md
  粒度: single
  上記の粒度に従って実装を完遂し、完了したタスクのチェックボックス更新まで行ってください。
```

**次タスク特定フロー**（task-executor完了後）:
1. `specs/stories/{STORY_ID}-{title}/tasks/task-*.md` パターンの全タスクファイルをスキャン
2. 各タスクファイルを開き、未完了チェックボックス`[ ]`の有無を確認
3. フェーズ番号→連番の順（phase1-001 < phase1-002 < phase2-001）で未完了タスクを並べる
4. 粒度（`single` / `batch(N)` / `phase`）をユーザー指示 or デフォルトで決め、task-executorに渡すタスクファイル一覧を確定する
5. 未完了タスクがあれば、そのタスクファイル一覧を指定してtask-executorを呼び出し
6. 全タスク完了なら品質保証フェーズへ進む

**フェーズ完了時の品質ゲート（必須）**:
- task-executorに渡す「次のタスク」が**次フェーズ**に進む場合、直前フェーズが完了しているため品質ゲートを通す
- 判定方法（どちらかを満たせばOK）:
  - 直前に完了したタスクが「Phase{N} 完了チェック（証跡作成）」等のフェーズ完了タスク
  - 直前タスクのphaseと、次に実行する未完了タスクのphaseが異なる（例: phase1-* 完了後に phase2-* へ進む）
- 対応:
  - **フェーズ最終タスク（=フェーズ完了タスク、またはそのphaseの最後の未完了タスク）**をtask-executorに依頼する際、プロンプトに必ず追記する:
    - 「このタスクは Phase{N} の最終タスクです。完了報告前に `/quality-fixer` を実行して `status=approved` を確認してください。」

### テスト情報の伝達
acceptance-test-generator実行後、work-planner呼び出し時には以下を伝達：
- 生成された統合テストファイルパス
- 生成されたE2Eテストファイルパス
- 統合テストは実装と同時、E2Eは全実装後に実行する旨の明示

## 実装専門原則（オーケストレーター・実装エージェント向け）

### 🚨 最重要原則：調査OK、実装STOP

**すべてのEdit/Write/MultiEditツール使用前にユーザー承認が必須**

理由：ユーザーの意図と異なる実装を防ぎ、正しい方向性を確保するため

### 実装実行プロセス

#### 実行フロー（必須手順）
1. **TodoWriteでタスク分解** → なければ実装ステップに進めない
2. **Edit/Write/MultiEdit使用** → ユーザー承認が必須
3. **実装実行** → 品質チェックエラーは完了条件を満たさない
4. **ファイル数カウント** → 閾値超過で自動停止

#### TodoWriteと実装の統合
**実行ルール**：
- TodoWriteなしでEditツール使用: ルール違反として停止
  理由：タスク管理なしでは進捗追跡と品質保証ができないため

#### 実装前提条件
1. **TodoWriteのタスク** → in_progressステータスが存在すること
2. **ユーザー承認記録** → Edit/Write前に明示的承認があること
3. **品質チェック結果** → エラー0でなければ完了不可

#### 禁止事項（実装時）
- **TodoWriteなしのEdit使用** → ルール違反
- **承認なしEdit/Write/MultiEdit** → 承認待ちに移行
- **品質エラー残存での完了宣言** → 完了条件を満たさない

### 実装時の行動制御（失敗防止）

#### 自動停止トリガー（必ず停止）
- **5ファイル以上の変更検出**：即座停止、影響範囲をユーザーに報告
  理由：大規模変更は事前計画とレビューが必要なため
- **3ファイル編集完了**: TodoWriteの更新を強制（更新しないと次のEditツール使用不可）
  理由：進捗確認と方向性の再確認が必要なため

#### エラー修正衝動対処
1. エラー発見 → **一時停止**
2. 根本原因分析（なぜ？を5回繰り返して真因を特定）
3. 対処計画提示
4. ユーザー承認後に修正

#### 集中時のルール無視防止
**測定可能な強制停止基準**：
- **連続エラー修正2回目**: 一時停止し、根本原因分析を実施
- **Editツール5回使用**: 影響範囲レポートの作成を強制
- **同一ファイル3回編集**: リファクタリング検討の強制停止

### 品質チェックの責務分担

#### 各タスク実行時
task-executorが以下を実行：
1. tasksファイルの完了条件に従って基本品質チェック
   - TypeScript strict mode: エラー0件
   - Biome lint: エラー0件
   - 追加したテスト: すべてパス

#### フェーズ完了時（必須）
**フェーズ最終タスク**（フェーズ完了チェックタスク、またはそのphaseの最後の未完了タスク）を実行するtask-executorが以下を実行：
1. `/quality-fixer`スキルを呼び出してプロジェクト全体品質チェック
2. `status=approved` を確認してから完了報告（blockedの場合は理由とユーザー判断ポイントを明示）

**目的**: 設計フェーズ完了をmeta.jsonに記録する

**実行内容**:

   - github_branch: ブランチ名

**目的**: 実装フェーズ完了をmeta.jsonに記録し、PRを作成
